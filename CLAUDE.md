## What This Is

This is a fork of XMage (Java MTG rules engine) used as the reference implementation and test harness for the **stax** project — a C++ MTG rules engine at `/home/inolen/projects/stax`. The XMage fork contains a custom data collector (`StaxReplayWriter`) that records XMage test games as `.mtg` replay files, which the stax C++ engine then replays to verify correctness.

## Build & Test

```bash
# Build everything (from ext/xmage/)
mvn clean install -q
# Build just the core library (MUST use clean — incremental builds skip recompilation)
mvn clean install -pl Mage -q
# Generate a replay file from random decks
mvn test -pl Mage.Tests \
  -Dtest=StaxReplayGenerator#generate \
  -Dstax.set=M11 \
  -Dstax.seed=42 \
  -Dxmage.staxReplayWriter.replayFile=../../../tests/replays/data/replay-M11-42.mtg
```

**Critical**: Always use `mvn clean install` (not `mvn install`) when rebuilding Mage. Without `clean`, changed `.java` files are NOT recompiled and tests run against stale jars.

## Architecture Notes

### StaxReplayWriter Event Flow

The writer hooks into XMage via `DataCollectorServices` callbacks. Key design:

- **Deferred choose queue**: XMage AI pre-fills cost targets during simulation. When the real game replays the chosen action, `Targets.makeChoice()` sees targets already chosen and skips `Player.choose()`. The writer catches these at the skip point and defers them until after the cast/activate event is written.
- **Pending events**: Non-pregame actions are queued in `pendingEvents` and flushed when a priority pass or phase change occurs, ensuring correct ordering.
- **Instance tracking**: The writer tracks per-player card instance counts on the battlefield to disambiguate multiple copies (e.g., `"Soldier Token":2`).

### Test Data Generation

`.mtg` files are NEVER manually edited. They are always regenerated by running XMage tests with the stax replay data collector enabled. The output directory flag writes files directly to the stax test data directory.
